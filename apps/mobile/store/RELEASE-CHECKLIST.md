# VoltAI — Production / Store Release Checklist

Honest status of what's ready to ship and what still blocks a public release.
Verified against `app.json`, `app.config.ts`, `eas.json`, `lib/`, and app source at HEAD on 2026-08-15
(supersedes the 2026-08-09 pass; this revision also re-checks the backend claims against
`/ARCHITECTURE.md` and `apps/api/RUNBOOK.md`).

Legend: **(A)** done · **(B)** needs the owner / external action · **(C)** risks that can block or reverse a release.

Backend deployment is **not** described here beyond what blocks the store release. The two sources of
truth are **`apps/api/RUNBOOK.md`** (how to deploy and operate the phone backend) and
**`/ARCHITECTURE.md`** (why it is built that way). Where this file and those disagree, they win.

## (A) DONE — verified in the project

- **App icon** — `assets/images/icon.png` present and wired via `app.json` `expo.icon`. (Requirement: 1024×1024, no alpha channel — keep it opaque; Apple rejects icons with transparency.)
- **Adaptive Android icon** — foreground / background / monochrome layers configured under `android.adaptiveIcon`.
- **EAS build profiles** — `eas.json` defines `development`, `preview`, and `production` profiles. Dev/preview build internal APKs; production builds an Android **app-bundle (.aab)** with `autoIncrement`.
- **Bundle identifiers set on both platforms** — iOS `ios.bundleIdentifier = uz.voltai.app`, Android `android.package = uz.voltai.app`. Matches the intended `uz.voltai.app`.
- **Export-compliance flag** — `ITSAppUsesNonExemptEncryption: false` set in `app.config.ts` iOS `infoPlist` (standard HTTPS/TLS only), so the App Store export-compliance prompt is skipped each submission.
- **Location usage strings present** — iOS `NSLocationWhenInUseUsageDescription` (foreground / "When In Use" only) is set; Android requests `ACCESS_COARSE_LOCATION` + `ACCESS_FINE_LOCATION`. The Yandex MapKit plugin also carries a matching when-in-use permission string. No background-location entitlement is requested (correct — the app only needs foreground location).
- **Account-free ⇒ no in-app account-deletion requirement** — the app has no sign-in and no server-side user records. Everything the user configures lives in on-device AsyncStorage: per `lib/storage/storageKeys.ts` that is `vehicleProfile` (legacy, read once to migrate), `garage`, `stationsCache`, `appSettings`, `planIndex`, plus one `voltai.plan.<id>.v1` body key per saved trip. (Corrected 2026-08-15 — an earlier revision of this line claimed the only stored key was `themePreference`; that key does not exist. Theme preference is one field inside `appSettings`. The account-free conclusion is unchanged.) Google Play's account-deletion / Data-deletion URL requirement and Apple's in-app account-deletion requirement do not apply. (You will still answer "no account" truthfully on the store forms — see B.)
- **Splash screen** configured (light + dark) via `expo-splash-screen`.

## (C) RISKS — can block, delay, or reverse a release

- **CRITICAL — the backend is built but not yet exposed at `api.voltai.uz`.**
  *(Rewritten 2026-08-15. The previous version of this bullet said the phone backend "fundamentally cannot serve distributed users" and told the owner to move to a cloud host. That was written before the Cloudflare Tunnel decision and is wrong on the facts; it is recorded here only so nobody acts on it. The phone **is** the intended production backend by design: see `/ARCHITECTURE.md` for why and `apps/api/RUNBOOK.md` for how.)*
  - **What exists.** One always-on Android phone runs, together: the Express API (Node LTS under Termux, port 8080, supervised by runit, autostarted by Termux:Boot, held awake with `termux-wake-lock`), the operator scrapers in-process on a randomized 3–5 min self-rescheduling loop (`SCRAPE_MIN_MINUTES`/`SCRAPE_MAX_MINUTES`, plus one scrape immediately on boot, each cycle ending with an inline merge), and the database as an embedded SQLite file (`node-sqlite3-wasm`). It currently serves **1,226 canonical stations** (tokbor 677, spectre 373, beon 89, k-watt 87), merged down from 2,005 raw rows. MongoDB/Atlas is retired.
  - **What's missing is reachability, not a backend.** Public access is a **Cloudflare Tunnel**: `cloudflared` dials **outbound** from the phone, so there is no inbound port, no public IP requirement and no CGNAT problem. Nothing needs to be port-forwarded. Client capacity is absorbed by **Cloudflare edge caching** of `/api/stations*`, `/api/stations/statuses` and `/api/plan*` — which is why the Cache Rules below are mandatory rather than an optimization.
  - The stations client defaults to `https://api.voltai.uz` (`lib/stations/stationsClient.ts`), and the `production` EAS profile sets `EXPO_PUBLIC_API_BASE_URL=https://api.voltai.uz` — **but `api.voltai.uz` currently returns HTTP 500 `FUNCTION_INVOCATION_FAILED` (verified 2026-08-15).** A production build today would launch to an empty map showing a "Could not load stations — pull to retry" pill. (As of 2026-08-15 the client **no longer ships fabricated fallback stations**: the `MOCK_STATIONS` fixture — which included invented UZS prices and the US brand "EVGo" — was removed, so a fresh install with no reachable API now shows an honest empty/error state instead of fake pins. The blocker is therefore reduced to "make the API reachable," not "stop showing fake data.")
  - **That 500 is not a bug to debug.** The `api.voltai.uz` record is still a CNAME to the retired **Vercel** deployment (`…vercel-dns-017.com`), and that platform cannot host this API at all: it needs a **writable filesystem** (the SQLite file) and a **long-lived process** (the scrape loop), neither of which a serverless function has — see `apps/api/docs/ROUTE_PLANNER.md` §8.1 (line 684), which spells out both structural causes and says in as many words "do not debug the function". There is nothing to fix on Vercel; the record has to move.
  - **API base URLs (corrected 2026-08-15 — fixed in commit `911b693`).** Only the **`development`** profile still points at `http://127.0.0.1:8080` (`eas.json:12`), which resolves to the owner's own backend phone via `adb reverse` and is correct for that profile. **`preview` (`eas.json:20`) and `production` (`eas.json:27`) both target `https://api.voltai.uz`.** Also: `apps/mobile/.env` is **not** checked in — it is gitignored by the repo-root `/.gitignore:12`; an earlier revision of this bullet claimed otherwise.
  - **Required before public release — the tunnel cutover, in order:**
    1. Move the `voltai.uz` DNS zone to Cloudflare — `apps/api/docs/GATES.md` §Gate 2. **Still open:** as of 2026-08-15 the nameservers are `rdns1/2/3.ahost.uz`, not Cloudflare. This is the only gate left and it blocks everything below.
    2. Remove the Vercel entrypoint (`apps/api/vercel.json`, `apps/api/api/index.ts`) so the broken function can never redeploy over the new record. ⏳ **OUTSTANDING** — not done, and deliberately not done as part of this doc pass; it is a live-config change for the owner to make.
    3. `cloudflared tunnel route dns voltai-api api.voltai.uz`, with ingress to `127.0.0.1:8080` — `apps/api/RUNBOOK.md` §4. Keep the `path: ^/ingest → http_status:404` ingress rule so `/ingest` is never reachable through the edge.
    4. Add the Cloudflare **Cache Rules** (Cache Eligibility = *Eligible for cache*) on `/api/stations*`, `/api/stations/statuses` and `/api/plan*`, and confirm `cf-cache-status: HIT`. Extensionless JSON is *not* cached by Cloudflare's defaults no matter what `Cache-Control` the origin sends, so without this rule every client poll lands on the phone.
    5. Confirm `https://api.voltai.uz/api/health` and `/api/health/detail` both answer **through the edge**, with `stale:false` and sane per-source `lastIngestAt` values, then verify a real `preview` build points at it and renders stations.
    6. Prove **zero-touch reboot recovery** on the phone, and stand up the external uptime + staleness alerts — see the "Single point of failure" bullet below. Neither exists yet, and both are release prerequisites, not follow-ups.
  - **Do NOT move the API to a cloud host.** Vercel / Docker / AWS is not the plan and is not a fallback — the write-and-long-lived-process requirements above are structural. Only the marketing website (`voltai.uz`, `apps/web`) is on Vercel, and that part is correct.
  - Plaintext `http://` base URLs are blocked by App Transport Security (iOS) / cleartext-traffic policy (Android) — production **must** be HTTPS. (`app.config.ts` enables `usesCleartextTraffic` for Android; that exists only so `development` builds can reach `127.0.0.1:8080`, and both the `preview` and `production` profiles' HTTPS base URLs make it moot.)

- **Single point of failure — one phone.** This is the real, narrower version of the "always-on / scalability" worry, and it stays on the list. It is **not** an argument for a cloud host; it is the reason the following are mandatory rather than optional:
  - **External uptime check** on `https://api.voltai.uz/api/health` — from off the phone, so it catches the phone being dead, asleep, or off Wi-Fi.
  - **Staleness alert** on `/api/health/detail`. Note the sharp edge: `stale` only detects a **stopped scheduler** — `lastScrapeAt` is stamped at the end of every cycle even when every source failed. To catch dead sources you must alert on the per-source `lastIngestAt` values in the same payload.
  - **Local watchdog — written, but not supervised.** `apps/api/scripts/termux/watchdog.sh` exists, but `scripts/termux/install-services.sh` registers only `voltai-api` and `cloudflared` as runit services; `apps/api/RUNBOOK.md:85` still tells you to run the watchdog as a hand-typed `while true` loop, which dies with the Termux session. Until it is a third runit service, the phone's local self-heal does not survive unattended operation.
  - **Deferred cloud read-replica** (`/ARCHITECTURE.md` §6) — ⏳ **NOT BUILT.** Designed, not implemented. It is the documented answer to "the phone died", and until it exists the phone dying means the app has no data source.
  - **Device risk — accepted, and its mitigations are mandatory.** The backend device is an **ASUS Zenfone 10 (AI2302) running Android 15** — the exact OS `apps/api/RUNBOOK.md:11-15` names as the riskiest for this (it kills long-running Termux processes even with wake-lock and battery-unrestricted; the RUNBOOK's stated preference is Android 12–14). There is no second phone, so the preference cannot be met. The RUNBOOK's Android-15 mitigations are therefore not optional: phantom-process killing disabled, battery optimisation set to Unrestricted for Termux, `termux-wake-lock` held. Add a verified **zero-touch reboot recovery** test before launch — prove the API comes back **without anyone touching the phone**.

- **Third-party data sourcing — store-policy rejection / takedown risk.**
  - Station locations and live availability are obtained by **reverse-engineering several operators' private app APIs**. This is the core legal/policy exposure:
    - **Apple App Store Review Guideline 5.2.2** (use of a third-party's service/data/API without authorization) can cause rejection or removal. **Guideline 5.2.1 / 5.2.5** (intellectual property) and **4.0/4.1** (design/copycat) are also in scope.
    - **Trademark & logo use** — operator names and logos are bundled (`assets/operators/*.png`, extracted from the operators' own apps). Displaying third-party trademarks/logos without permission risks IP complaints on both stores and DMCA-style takedowns.
    - **Google Play** equivalents: **Intellectual Property** policy and **Impersonation / Misrepresentation** can trigger the same rejection/removal.
  - **Mitigations to consider:** obtain permission or a data-sharing agreement from each operator; use only publicly documented/authorized endpoints where available; drop or replace unlicensed logos with neutral markers; add clear "unofficial / not affiliated" attribution; be ready for a takedown by keeping the operator set configurable server-side.

- **Operational fragility of scraped data.** Availability depends on undocumented endpoints (OTP login-replay etc.) that operators can change or block at any time — one operator (Megawatt) is already blocked, by hardware attestation. Expect intermittent gaps; the app degrades gracefully (it supports "only available" filtering and per-operator display).
  - ✅ **Per-operator failure isolation: DONE** (verified 2026-08-15). `apps/api/scrapers/http/httpScraper.ts:116-140` (`scrapeAllHttpSources`) scrapes every source concurrently and catches per source, returning `{source, ok:false, error}` instead of throwing — one dead operator API never blocks the others, and a not-yet-logged-in source is `skipped` rather than counted as a hard failure. This was listed here as an open item; it is implemented.
  - ⚠️ **Still open — token expiry is a manual, silent failure.** The tokbor/beon login-replay bearers are ~365-day JWTs with **no refresh token** (Beon's is valid to 2027-08-07), so renewal is a hand-run OTP re-login. Nothing warns you before it lapses — this is precisely what the per-source `lastIngestAt` alert above is for.
  - ⚠️ **The auth token store is not in git.** `apps/api/data/auth-tokens.json` and `apps/api/data/tokbor-details.json` are gitignored, so a git-clone deploy to the phone silently loses Tokbor and Beon (766 of 1,226 stations) and strips names/prices from the remaining Tokbor pins. They must be copied to the device by hand — see `apps/api/RUNBOOK.md`.

- **Trip planner changes the data story — the store forms in (B) must be re-derived.** The app now ships a trip planner (`lib/plan/`), and `lib/plan/planClient.ts:112-127` sends the user's **origin and destination coordinates** to `GET /api/plan` on the VoltAI backend, which forwards them to a **third-party routing provider (MyTaxi)** server-side (`apps/api/src/services/routing/mytaxi.ts`). Consequences:
  - Location is **no longer "on-device only"** and **no longer "not shared"**. Both store declarations must say location data is transmitted, used for App Functionality (route planning), not linked to identity, and not used for tracking.
  - `store/privacy-policy.html` is also now inaccurate on this point — it states location is "never sent to our servers or anyone else" and that station requests "carry no personal identifiers". Update it **before** publishing it at the URL you paste into the stores.
  - Mitigating facts worth stating accurately rather than hiding: there are still **no accounts**, coordinates are not tied to any identifier, `MYTAXI_API_KEY` never ships in the client bundle (the call is server-side only), and route geometry is cached server-side so repeats are not re-sent. None of that makes the old "not collected" answer true.
  - An inaccurate Data-safety / nutrition-label declaration is an **enforceable post-launch removal ground** on both stores. Treat this as blocking, not cosmetic.

- **Features shipped since this checklist was first written — none of them were reviewed here.** The doc previously read as complete while describing only the map. Also in the store build and needing their own review pass: the **trip planner** (charge-stop planning, charge curves, `GET /api/plan`), the **garage** (multiple saved vehicle profiles, `StorageKeys.garage`), and **saved trips** (`StorageKeys.planIndex` + one `voltai.plan.<id>.v1` body per trip). All three are account-free and on-device apart from the planner's server call above. Screenshots, the store listing copy in `store-listing.md`, and the content-rating answers should all be checked against these, not just the map.

- **No monitoring, no backups, no working rollback.** ⏳ **NOT BUILT (2026-08-15).** Shipping to the public without them means a failure is invisible until users report it, and unrecoverable when it happens.
  - **Monitoring** — the external uptime check and the `lastIngestAt` staleness alert described above do not exist yet. Nothing currently watches the phone.
  - **Backups** — ✅ **BUILT (2026-08-15)**, ⏳ **not yet armed.** `apps/api/scripts/termux/backup.sh` + `restore.sh` now implement the nightly hot-SQLite-copy → gzip → `rclone` to Cloudflare R2 (14-day retention) design, registered as the `voltai-backup` runit service by `install-services.sh`. What remains is operational, not code: run `rclone config`, set `BACKUP_REMOTE` in the phone's `.env`, run one backup, and do one `restore.sh` dry run to prove it. Until that is done the phone's SQLite file and the `auth-tokens.json` store are still effectively unbacked-up — **arm it before public launch.**
  - **Rollback** — `apps/api/RUNBOOK.md` §Rollback documents a DNS-level rollback (repoint `api.voltai.uz`), but its own caveat records that there is **no warm origin** to roll back to — the previous record is the 500-ing Vercel function — and no tested backups. There is no way to revert a bad *code* deploy on the device itself, and no store-side rollback plan (Play halted rollout / new build; Apple requires a new submission). Decide both before the first public release. The mobile side has no remote kill switch or feature flags, so a bad client build can only be fixed by shipping another one.

- **Single API key exposure.** `EXPO_PUBLIC_*` values are embedded in the client JS bundle and are extractable. The Yandex MapKit key avoids that path — `app.config.ts` reads the non-prefixed `YANDEX_MAPKIT_API_KEY` and passes it to the `expo-yandex-mapkit` plugin, so it lands in the native config rather than the bundle — but it still ships inside the app package and can be pulled out of an APK/IPA. It should be restricted (by bundle id / platform) in the Yandex console to limit abuse.
